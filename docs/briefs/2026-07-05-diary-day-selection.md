# Бриф: выбор дня в WeekStrip дневника

**Роль этого файла:** продуктовый бриф + контракт процесса для автономного прогона (`/goal`). Правила репо (`AGENTS.md`, `docs/INDEX.md`, скиллы `.agents/skills/*`) остаются главными; этот бриф фиксирует продуктовые решения и порядок работы, чтобы агент не останавливался на продуктовых вопросах.

## Фича

В табе Diary верхний недельный календарь (`WeekStrip` в составе `TodayScreen`) сейчас display-only. Нужно: **тап по дню недели переключает дневник на эту дату** — ниже показывается таймлайн (лог событий) выбранного дня.

Технический контекст (проверено заранее):
- Примитив `src/design/primitives/WeekStrip.tsx` уже поддерживает `onSelectDay` с корректной a11y (role=button, `accessibilityState.selected`). Прокидывать его нужно из `DiaryWeekStrip` в `src/features/today/screens/TodayScreen.tsx`.
- Таймлайн уже рендерится инлайн в Diary через `useQuickLogTimelineRows`; неделя уже вычисляется от `selectedDate`.
- Визуал выбранного дня уже существует в атласе (закрашенный кружок) — **визуальных отклонений от дизайна нет**, меняется только поведение. Зафиксируй это в Design Lock как "behavior-only change, no visual deviation".

## Продуктовые решения (не обсуждаются в рамках этого прогона)

1. **Прошлые дни недели:** тап показывает таймлайн этого дня (только записи этой даты).
2. **Сегодня:** тап возвращает текущее поведение Diary без изменений (план-карточки, приветствие, таймлайн сегодняшнего дня).
3. **Будущие дни:** тапабельны, показывают empty state «записей ещё нет» (существующий стиль empty state). Не disabled.
4. **План-карточки и приветствие** показываются только когда выбран «сегодня»; для других дней — только таймлайн дня (заголовок даты + список).
5. **Quick Log (FAB)** всегда логирует «сейчас», независимо от выбранного дня. После логирования при просмотре прошлого дня новая запись там не появляется (она за сегодня).
6. **Без персиста:** уход с таба и возврат = снова «сегодня».
7. **Фильтры/режим истории таймлайна** не переделывать; они продолжают работать как сейчас для «сегодня». Если их совмещение с выбранным днём создаёт конфликт — для не-сегодняшних дней показывай таймлайн дня без чипов фильтров и зафиксируй это решение в план-доке.

## Скоуп-гард

- Если слой запросов (`src/lib/query`) уже позволяет выбрать записи за произвольную дату — используй его, расширяя контракты минимально.
- Если для произвольной даты нужен новый query-путь и он тянет за собой большой рефакторинг — **допустимый вариант этой итерации:** клиентская фильтрация уже загружаемых строк по дате выбранного дня в пределах текущей недели. Зафиксируй выбор и причину в план-доке.
- Не трогать: очередь Quick Log, схему БД, RLS, контракты `business-rules.ts`, навигационный контракт табов.

## Обязательный процесс (по AGENTS.md, с уточнениями)

1. **Linear:** создай issue в команде `PUP`, проект `PuppyPlan MVP`, с Task Contract (Goal / Non-goals / Constraints / Acceptance / Likely files / Verification). Веди статусы и прогресс по `docs/agents/linear-workflow.md`. **Фолбэк:** если Linear MCP недоступен — полный Task Contract в план-доке, пометка «Linear pending», продолжай работу.
2. **План:** `docs/plans/active/2026-07-05-diary-week-strip-day-selection.md` по шаблону репо, включая Design Lock (Stage 0) с фиксацией «behavior-only». **План-док — рабочий и компактный: не длиннее ~150 строк.** Не пиши исчерпывающую спецификацию — только фазы, acceptance-критерии, Design Lock и чек-лист; целься уложить фазу планирования в ~15 минут. **После плана — СТОП: покажи краткое резюме плана и жди явного подтверждения пользователя, затем продолжай.**
3. **TDD:** используй `.agents/skills/tdd/SKILL.md`. **Заранее одобрено для этой задачи: subagents для heavy/full-isolated TDD; фолбэк — lightweight TDD с reduced assurance тоже одобрен. Дополнительных подтверждений режима TDD не запрашивать.** Сначала падающие тесты: render-тесты анатомии/поведения (`src/test/*.render.test.tsx`) — выбор дня, empty state будущего дня, возврат на сегодня, a11y-состояния; юнит-тесты чистой логики выбора даты. Все новые строки — через типизированные i18n-ключи в EN/RU/ES.
4. **Гейт:** `npm run check` зелёный. Ничего не ослаблять (никаких ts-ignore/eslint-disable/правок конфигов).
5. **Чек-лист тест-кейсов** (отдельный раздел план-дока): минимум 10 кейсов. **Обязательные категории — каждая должна присутствовать в симуляторном прогоне, а не только в render-тестах:** позитивные (прошлый день с записями, сегодня, будущий день — если в текущей неделе есть будущие дни), граничные (понедельник/воскресенье недели), **минимум один a11y-кейс** (проверка лейблов/selected через иерархию вью), **минимум один кейс на локали RU** (переключение языка и проверка подписей дней/даты), регрессия (FAB Quick Log, фильтры, режим истории, переключение табов, undo удаления записи).
6. **Прогон на симуляторе:** только SE-профиль из AGENTS.md (`Grith iPhone SE 3 iOS 26.3`, UUID `5C46B6CC-9CC2-4326-84A3-2603E0F0F3C6`). Синтетические данные (насей записи за 2–3 разных дня недели через Quick Log или dev-средства). Прогони чек-лист через Maestro **CLI** (`maestro test` с ad-hoc YAML-флоу во временной директории вне репо — tracked harness добавлять запрещено по AGENTS.md), каждый кейс — вердикт PASS/FAIL + скриншот. Отчёт — в план-док и Linear.
   Уроки предыдущего smoke-прогона (обязательно):
   - iOS-сборка только через `ios/PuppyPlan.xcworkspace` (через `.xcodeproj` ломается).
   - В Maestro-флоу только **id-селекторы** (testID), текстовые `assertVisible` ненадёжны — не использовать.
   - Поэтому в рамках самой фичи добавь стабильные testID всем новым интерактивным/проверяемым элементам: per-day ячейки WeekStrip (например `week-strip-day-<date>`), заголовок/контейнер таймлайна выбранного дня, empty state будущего дня.
   - Android не входит в скоуп этого прогона.
7. **Фикс-луп:** найденные баги исправь (через тот же TDD), перепрогони упавшие кейсы, обнови отчёт. Если кейс не чинится за 2 итерации — зафиксируй блокер в отчёте и остановись.
8. **Git (одобрено заранее, ровно это):** ветка по Linear-имени (`dimaselenya/pup-…`, фолбэк `pup-<n>-diary-day-selection`), коммит(ы), push ветки, **draft** PR по шаблону репо с заполненным Work Tracking. Дождись зелёного CI (Verification workflow). НЕ одобрено: merge, правки main, релизные/прод-действия, изменения CI.
